## Что это

`dsh-gitea` подключает сессию DeepSeek Harness к вашему экземпляру Gitea или
Forgejo: агент получает 96 первоклассных инструментов (по умолчанию — через два
мета-инструмента `dispatcher`, которые открывают все операции и их схемы по
запросу) для issue, pull request'ов, ревью, CI, релизов и репозиториев, а вы —
страницу **Настройки → Gitea** и **бейдж Git-статуса** в заголовке сессии.
Ничего не парсится со страниц: каждый вызов — типизированный инструмент через
REST API, а токен разрешается из учётных данных DSH в момент вызова.
Читайте PR, делайте ревью, rebase, следите за CI, ставьте тег релиза и заводите
follow-up issue, не покидая чат.

*Форк [GooDAnDReaDY/dsh-gitea](https://github.com/GooDAnDReaDY/dsh-gitea) (MIT) —
что добавляет этот форк, см. в разделе
[На основе upstream](#на-основе-upstream).*

## Что с этим можно делать

- **Планировать работу.** Заводите один issue или пятьдесят, с метками (по
  имени *или* id), assignee и вехой одним вызовом; сначала проверяйте дубликаты
  и Definition of Done; просматривайте хронологию до ответа; массово
  переназначайте метки из одобренного пробного прогона.
- **Читать и менять код с контекстом.** Просматривайте ветки, теги, файлы,
  коммиты и diff'ы; ищите код локально, когда API forge не умеет; сравнивайте
  два ref'а перед слиянием.
- **Ревью как мейнтейнер.** Inline-комментарии с предложениями в один клик,
  одобрение или запрос изменений и сводка рисков по правилам — затронутые
  области, тесты, миграции, состояние слияния — плюс inbox ревью и предложения
  ревьюеров из `CODEOWNERS` и истории коммитов.
- **Сливать безопасно.** Гейт слияния проверяет описание, конфликты,
  одобрение, тесты и миграции; автослияние только при зелёном гейте; цепочки
  стековых PR с помощниками rebase; анализ конфликтов, который называет
  категорию каждого hunk'а и умеет применять решения. Деструктивные шаги
  требуют `confirm: true`, остальные сначала идут пробным прогоном.
- **Выпускать.** Планирование релизов по Conventional Commits, проверка semver,
  черновики changelog, теги, релизы, инспекция прогонов CI с анализом
  первопричины по логам и реестр пакетов (npm, PyPI, OCI, generic) с готовой
  к вставке клиентской конфигурацией.
- **Вести проект.** Отчёты о здоровье, ежедневный дайджест триажа, снимок
  дежурного, запланированные проверки только для чтения, защита веток,
  deploy-ключи, аудит безопасности и webhook'и, которые можно воспроизводить
  офлайн.
- **Работать там, где живёт репозиторий.** Git worktree для изолированных
  веток, граф коммитов в UI и поток issue → ветка → worktree → PR, который
  держит issue и код в синхроне.

## Требования

- DeepSeek Harness `0.2.x` — обе линии предрелизов `0.2.0` и `0.2.1` входят
  в peer-диапазон пакета.
- Node.js 20 или новее.
- `pnpm`, который может запускать DSH — Plugin Manager вызывает его для
  установки профиля.
- `git` на хосте DSH — для установки из git (запасной tarball его не требует).
- Экземпляр Gitea или Forgejo, доступный с хоста DSH по HTTPS, и API-токен
  к нему.

## Установка

Одна команда на хосте DSH. Это вся установка:

```bash
dsh plugin --profile web add dsh-gitea
```

`web` — имя профиля; используйте своё, если запускаете DSH с
`--profile <name>`. Пакет опубликован в публичном npm-реестре как
[`dsh-gitea`](https://www.npmjs.com/package/dsh-gitea).

Команда добавляет `dsh-gitea` в профиль и выбирает его bundle — пакет
объявляет `dsh.bundle`, поэтому строка плагина включается без отдельного шага
в Plugin Manager. Checkout для bootstrap не нужен, и `npm run dev:link`
**не** требуется: этот скрипт существует только для установок рабочей копии
через `link:`.

DSH сам применяет новый профиль — в web-профиле HMR следит за списком bundle;
в профиле без HMR перезапустите службу DSH. После этого обновите вкладку
браузера.

### Установка напрямую из репозитория

Плавающий `master`:

```bash
dsh plugin --profile web add https://git.pvlb.dev/dsh-plugins/dsh-gitea.git
```

Закреплено за тегом релиза:

```bash
dsh plugin --profile web add https://git.pvlb.dev/dsh-plugins/dsh-gitea.git#v0.8.4
```

Именно суффикс `.git` заставляет pnpm трактовать URL как git-репозиторий. Без
него URL скачивается как tarball, и установка падает с
`ERR_PNPM_TARBALL_HTTP_STATUS … 404`.

### Запасной вариант — tarball из реестра Forgejo

Используйте, когда с хоста DSH недоступны ни npmjs, ни git-remote:

```bash
dsh plugin --profile web add https://git.pvlb.dev/api/packages/dsh-plugins/npm/dsh-gitea/-/0.8.4/dsh-gitea-0.8.4.tgz
```

В любом случае пакет самодостаточен — `lib/index.js` плюс
`cordis.patch.yml` — а его DSH peer'ы берутся из профиля.

## Настройка

Достаточно двух настроек; остальное на странице можно оставить по умолчанию.

1. **URL экземпляра.** Откройте **Настройки → Gitea** — или **Plugins →
   dsh-gitea → Configure** — и задайте `baseUrl`, например
   `https://git.example.com`.
2. **Токен.** В Forgejo/Gitea откройте **Settings → Applications → Generate
   token** с областями repository, issue и pull-request (`read:user`
   покрывает `gitea_whoami`). Затем сохраните секрет в учётных данных DSH под
   именем, которое ожидает форма — `GITEA_TOKEN`, если вы не меняли
   `tokenEnv`.

   Хранилище — скрытый файл `~/.dsh/.credentials.yaml`; на верхнем уровне
   `version: 1`, затем `records:` и `refs:`. Добавьте имя в `refs:`:

   ```yaml
   refs:
     GITEA_TOKEN: <токен, который вы только что создали>
   ```

   Если файл уже существует, влейте эту строку в его блок `refs:`, остальное
   не трогайте. Новому файлу нужны `version: 1` и блок выше. Другие редакторы
   ключей DSH пишут в то же хранилище, так что этот файл — просто прямой путь
   для имени, которым больше никто не управляет.

Форма настроек принимает **имя** учётных данных, а не токен — значение, похожее
на токен, отклоняется. Хранилище учётных данных DSH перезагружает файл при
изменении и разрешает секрет при каждом вызове, поэтому новый или
ротированный токен применяется к следующему вызову инструмента без
перезапуска.

Опционально: задайте `defaultOwner` и `defaultRepo`, чтобы инструменты без
`owner`/`repo` откатывались к вашему обычному репозиторию.

### Набор инструментов — держите нагрузку небольшой

Схема каждого зарегистрированного инструмента привязывается к каждому запросу,
поэтому у плагина есть переключатель пресетов. **По умолчанию — `dispatcher`**
(с 0.8.9): два мета-инструмента, которые оставляют достижимыми все 96 операций,
пока постоянная нагрузка держится около 8.5 KB вместо ~60 KB. Поставьте
`preset: full` — в конфиге или в выпадающем списке настроек — если нужны 96
типизированных инструментов как обычные функции; сузьте поверхность сильнее,
если рабочему пространству нужны только issue или только ревью PR.

```yaml
- id: dsh-gitea
  config:
    preset: dispatcher  # dispatcher (по умолчанию) | core | issues | prs | repos | ops | full | none | custom
    tools: []           # glob-allowlist; непустой заменяет пресет
    excludeTools: []    # шаблоны, удаляемые после пресета/allowlist
    legacyAliases: false
```

| Пресет | Инструменты | Байт схемы | ≈ токенов |
|:--|--:|--:|--:|
| `dispatcher` (по умолчанию) | 2 | 8,973 | ~2.4k |
| `full` | 96 | 65,159 | ~17.6k |
| `core` | 15 | 11,640 | ~3.1k |
| `issues` | 22 | 15,586 | ~4.2k |
| `prs` | 27 | 17,480 | ~4.7k |
| `repos` | 17 | 12,026 | ~3.3k |
| `ops` | 30 | 20,067 | ~5.4k |
| `none` | 0 | 0 | 0 |
| `full` + `legacyAliases` | 133 | 107,157 | ~29k |

- `core` — 15 горячих инструментов; доменные пресеты не пересекаются, а их
  объединение — `full`. `*` — единственный wildcard, и шаблон, не совпавший ни
  с чем, сообщается в форме настроек и в логе, а не игнорируется молча.
- `legacyAliases` (по умолчанию **выключено** с 0.8.5) снова публикует 37
  имён-алиасов до 0.8. Они дублируют свои канонические схемы, поэтому стоят
  ~42 KB нагрузки; вызов алиаса всё равно разрешается, даже если он не
  опубликован.
- Сохранение другой поверхности немедленно перерегистрирует инструменты (без
  перезапуска). `preset: none` — для рабочих пространств, где агент не должен
  видеть инструменты Gitea.
- `dispatcher` был необязательным пресетом в 0.8.6–0.8.8, а с 0.8.9 это
  **значение по умолчанию**. Два мета-инструмента, `gitea { operation, args }` и
  `gitea_help { operation }` (возвращает JSON Schema одной операции как результат
  инструмента). Реестр **стабилен** — без динамической регистрации — поэтому
  префикс запроса остаётся кэшируемым, а каждая операция по-прежнему достижима;
  `preset: full` возвращает типизированную поверхность одной строкой. Конфиги,
  где пресет уже сохранён, сохраняют своё значение, так что смена умолчания
  касается только установок, которые его ни разу не выбирали. Компромисс измерен,
  а не теоретический: на пяти реальных задачах триажа (2026-10) шаг стоил 41.1k
  токенов вместо 58.2k (−29 %), но агентам потребовалось на 30 % больше шагов
  (раунд-трипы за help и повторы из-за имён аргументов), поэтому **итог** ниже
  лишь примерно на 8 %, а с учётом стоимости (попадание в кэш ≈ 0.26× свежего)
  — примерно на том же уровне. На коротких задачах ожидайте паритет, скромный
  выигрыш — после ~10 шагов; это **не** волшебный экономитель токенов (#51).
  Неизвестные аргументы возвращаются понятной ошибкой с перечнем допустимых,
  поэтому повторы дешёвы.

## Проверка

- **Настройки → Gitea** существуют и перечисляют поля; **Plugins** показывает
  `dsh-gitea` со страницей **Configure**. `plugin_manager action=list_bundles`
  показывает строку и её включённость.
- Попросите агента выполнить **`gitea_whoami`**. Он вернёт пользователя
  Forgejo, стоящего за вашим токеном, — это одной командой доказывает
  `baseUrl`, учётные данные и области токена.
- Откройте сессию в git-рабочем пространстве: в заголовке сессии появится
  **бейдж Git**.

## Устранение неполадок

| Симптом | Причина | Исправление |
|:--|:--|:--|
| `ERR_PNPM_TARBALL_HTTP_STATUS … 404` или ошибка разбора JSON при добавлении | в URL не было `.git`, и pnpm скачал его как tarball | добавьте `.git` или установите tarball по URL выше |
| `spawn pnpm ENOENT` или `dsh: pnpm was not found` | в `PATH` службы DSH нет `pnpm` | укажите его в патче профиля — `plugin-manager.pnpmCommand: /opt/node/bin/pnpm` (ваш абсолютный путь) — и повторите |
| Строка сообщает `failed to import` или `Cannot find package '@deepseek-ai/schemastery'` | установка рабочей копии через `link:` без разрешения peer'ов; установка из git или tarball так не делает | выполните `npm run dev:link` в этом checkout, затем выключите и включите bundle |
| В настройках нет пункта **Gitea** | bundle не выбран или браузер всё ещё запускает старый клиентский bundle | проверьте `plugin_manager action=list_bundles`, сделайте жёсткое обновление (`Ctrl+F5`), перезапустите DSH, если в профиле нет HMR |
| Инструменты отвечают `401`/`403`, хотя форма показывает имя учётных данных | этих учётных данных нет или у токена не хватает областей | создайте их в `refs:` с точным именем `tokenEnv`; перегенерируйте токен с областями repository, issue и pull-request |
| `403` со страницы Gitea по имени хоста LAN/Tailscale | сборка до 0.8, чей страж запросов откатывался только к loopback | обновитесь до 0.8.1 или новее, затем перезагрузите Host-половину |

## Набор инструментов

**96 первоклассных инструментов** (все публикуются пресетом `full`; пресет по
умолчанию `dispatcher` дотягивается до каждого из них через два мета-инструмента)
плюс **37 алиасов совместимости**, опциональных с 0.8.5. Инструменты уровня
репозитория принимают необязательные `owner`/`repo` (откат к
`defaultOwner`/`defaultRepo`, затем к git origin сессии), и каждый инструмент
принимает селектор `instance` для мультиэкземплярных конфигураций.
Деструктивные инструменты требуют `confirm: true`, а более рискованные
помощники сначала выполняют пробный прогон, так что агент может
предварительно посмотреть: ничего не сливается, не удаляется и не пушится
случайно.
37 алиасов — это старые имена одиночных действий (`gitea_ci_status`,
`gitea_label_list`, `gitea_release_create`, …); каждый сопоставлен одному
каноническому инструменту плюс действие по умолчанию, поэтому существующие
prompt'ы и скрипты продолжают работать.

| Область | Инструменты | Что покрывает |
|:--|--:|:--|
| Планирование: issue, метки, вехи | 22 | создание, триаж, шаблоны, дубликаты, массовые операции, issue → PR |
| Ревью и слияние | 27 | PR, inline-ревью с предложениями, гейты слияния, rebase, стеки, конфликты |
| Репозиторий и история | 11 | ветки, теги, тела файлов, коммиты, сравнение, поиск, состояние зеркала |
| Эксплуатация и управление | 17 | здоровье, дайджесты триажа, запланированные проверки, защита веток, webhook'и, организация, wiki, пользователи |
| Локальный git и worktree | 7 | worktree, граф коммитов, карточки действий |
| Релизы | 12 | релизы, semver и changelog, прогоны CI и анализ логов, пакеты, синхронизации, инциденты |

### Планирование: issue, метки и вехи — 22 инструмента

*Вся поверхность планирования: завести, разобрать и держать backlog честным.*

- **`gitea_issue_list`** — issue по состоянию с явной пагинацией; без
  молчаливого ограничения строк.
- **`gitea_issue_get`** — один issue, опционально с комментариями.
- **`gitea_issue_create`** — заголовок, тело, метки (имена или числовые id),
  assignee и веха одним вызовом.
- **`gitea_issue_update`** — изменить заголовок, тело или состояние.
- **`gitea_issue_close`** — закрыть issue за один шаг.
- **`gitea_issue_comment`** — добавить комментарий.
- **`gitea_issue_comments`** — список комментариев, каждый помечен
  `mine: true/false`.
- **`gitea_issue_comment_delete`** — удалить свой комментарий; пробный прогон,
  если нет `confirm: true`.
- **`gitea_issue_search`** — поиск по всему экземпляру с фильтром по
  репозиторию, состоянию, типу или меткам.
- **`gitea_issue_set_assignee`** — передать issue логину.
- **`gitea_issue_timeline`** — комментарии, события и смены статуса в
  хронологическом порядке.
- **`gitea_issue_lint`** — предварительная проверка разделов problem, impact,
  priority, DoD, boundaries, dependencies и verification; только
  рекомендательно.
- **`gitea_issue_duplicates`** — ранжировать вероятные дубликаты по сходству
  заголовка/тела до создания.
- **`gitea_batch_issue_ops`** — задать метку, assignee или веху многим issue;
  пробный прогон без подтверждения.
- **`gitea_issue_templates`** — перечислить и проверить YAML-формы issue
  Gitea (плагин поставляет свой набор; можно указать другую папку).
- **`gitea_issue_flow`** — спланировать имя ветки и путь worktree для issue
  или открыть PR из head-ветки.
- **`gitea_issue_to_pr`** — выполнить цикл issue → ветка → worktree → PR, с
  созданием worktree и PR за флагами.
- **`gitea_labels`** — список, создание, удаление, установка на issue или
  добавление; список показывает числовые id, которые используют другие
  действия.
- **`gitea_label_bootstrap`** — идемпотентно синхронизировать домашний набор
  меток pvlb.dev (или устаревшую таксономию «upstream»); пробный прогон без
  применения, никогда не удаляет чужие метки.
- **`gitea_label_auto`** — показать действия workflow, которые подразумевают
  метки issue; только чтение.
- **`gitea_milestones`** — список, создание, обновление и удаление вех,
  включая сроки.
- **`gitea_reactions`** — список, добавление или удаление emoji-реакций на
  issue и комментариях.

### Ревью и слияние: pull request'ы, ревью и гейты — 27 инструментов

## За пределами инструментов

**Страница настроек, которая действительно сохраняется.** **Настройки →
Gitea** — первоклассная страница, и та же форма доступна из
**Plugins → строка bundle → Configure**. Она покрывает подключение, *имя*
учётных данных, значения по умолчанию, таймауты, переписывание URL за
прокси, секрет webhook'а, push-уведомления, фоновый планировщик, напоминание
DoD, дополнительные экземпляры и переключатель обновлений. Форма работает
через `GET`/`POST /dsh-gitea/config`, сообщает, доступна ли она для записи,
вместо того чтобы исчезать на удалённых страницах, и принимает только ссылку
на учётные данные — никогда токен.

**Бейдж Git там, где вы уже смотрите.** Заголовок сессии показывает ветку,
маркер грязных изменений, счётчики ahead/behind, номер открытого PR, `CI✗`
при неудачных проверках и предупреждение об отставании зеркала. Один клик
открывает панель с четырьмя вкладками: **Status**, **Graph & CI** (граф
коммитов со статусами CI по каждому коммиту), **Events & PRs** (живой поток
событий и контекст PR) и **Hub**. Заголовок панели начинается с **логотипа
Gitea или Forgejo и имени репозитория как одной ссылки** на веб-страницу
репозитория — URL берётся из `origin` remote checkout'а, а иконка (Forgejo,
Gitea или скрыта) — настройка.

**Webhook'и внутрь, события наружу.** Направьте webhook Gitea/Forgejo на
`POST /dsh-gitea/webhook`, и payload проверяется через HMAC-SHA256 с
использованием учётных данных, указанных в `webhookSecretEnv` — без секрета
ответ 401, а не обработка payload'а. Принятые события попадают в кольцевой
буфер последних 50 в памяти, доступны для чтения по `GET /dsh-gitea/events`
и стримятся в браузер по SSE через `GET /dsh-gitea/sse`. Опциональный
`notifyWebhook` пересылает оповещения о новых PR и неудачных CI во внешний
канал.

**Hub для кнопок UI.** `GET /dsh-gitea/hub` агрегирует issue, PR, CI runner'ы
и worktree для панели; `POST /dsh-gitea/hub` диспатчит действия, которые
используют UI и карточки действий: одобрить, слить, закрыть, открыть/переключить
worktree, собрать мусор worktree, анализ логов CI, осмотр стековых PR и
разрешение конфликтов. Каждая его ветка находится за тем же защитным
барьером Host/Origin/Connection, что и остальные маршруты.

**Шаблоны issue в комплекте.** Семь YAML-форм issue Gitea идут в коробке
(bug, feature, tech-debt, security, incident, research, config-change), и
инструмент шаблонов проверяет, что форма всё ещё содержит нужные Gitea поля,
прежде чем вы её опубликуете. Инструмент bootstrap репозитория сажает тот же
набор в новые репозитории.

**Потоки ревью и передачи.** Issue можно спланировать в ветку и worktree,
превратить в черновик PR и вернуть в inbox ревью. Ревью PR основано на
правилах и только для чтения, если вы не попросите комментариев; AI-ревью
публикуется только по команде.

**Фоновый триаж, по умолчанию выключен.** Включите планировщик, и он будет
запускать дайджест триажа по интервалу, отправлять его в опциональный webhook
и делать пробную проверку сборки мусора worktree — ничего не удаляется.
Напоминание DoD (тоже выключено по умолчанию) добавляет неблокирующую заметку,
когда прогон инструмента изменил git-файлы без ссылки на issue или PR.

**Сервисы, которые могут компоновать другие плагины.** `dshGitea` реализует
контракт `dsh-drives.task-provision.v1` (`isConfigured()`, `createIssue()`,
идемпотентно по `externalRef`, с разрешением имён меток по пути), поэтому
доска задач может создавать issue в Gitea. `giteaEvents` — это fan-out для
событий webhook'ов (`subscribe`, `on('event')`, `emit`, `subscriberCount`),
поэтому второй плагин может реагировать на активность forge без опроса.

## Безопасность по умолчанию

- **Токен никогда не живёт в плагине.** Форма и конфигурация хранят *имя*
  учётных данных; DSH разрешает секрет в момент вызова. Значение, похожее на
  токен, отклоняется, и ничего секретного не пишется в репозиторий или лог.
- **Каждый кастомный маршрут огорожен.** `lib/http-guard.js` делегирует DSH
  Connection, когда он смонтирован (401 для неаутентифицированного удалённого
  клиента, 403 для отклонённого origin), иначе откатывается к loopback-only,
  fail-closed.
- **Webhook'и аутентифицированы.** `POST /dsh-gitea/webhook` проверяет
  подпись HMAC-SHA256; отсутствующий секрет отвечает 401 вместо обработки
  payload'а.
- **Рискованные записи под гейтом.** Деструктивные инструменты требуют
  `confirm: true` (более рискованные помощники сначала идут пробным прогоном),
  а обновление в один клик требует и loopback-запроса с
  `x-dsh-plugin-update`, и переключателя `updates`.
- **Публикуемое дерево сканируется.** `npm run test:leaks` валит сборку при
  приватных путях, приватных scope, литералах токенов или кириллице в
  поставляемом JS.

## На основе upstream

`dsh-gitea` — форк
[`GooDAnDReaDY/dsh-gitea`](https://github.com/GooDAnDReaDY/dsh-gitea) (MIT),
ответвлённый от upstream `abfd952` и поддерживаемый на forge pvlb.dev. Мы
запускаем его в собственном развёртывании DeepSeek Harness и несём исправления
и склеивающий код, которые ему понадобились.

**За upstream наблюдаем, но не разрабатываем против него.** Его публичное
дерево GitHub генерируется из приватного исходного репозитория автора — каждый
коммит это `chore(publish): sanitized tree from <sha>` — поэтому PR против
сгенерированных файлов (таких как `lib/client.js`) может быть отброшен при
следующей публикации. Мы синхронизируемся осознанно, когда изменение upstream
действительно важно, держим набор патчей маленьким и отправляем улучшения
наверх минимальными переносимыми патчами, когда это имеет смысл
(`lib/http-guard.js` — самый чистый кандидат).

Что форк добавляет поверх upstream:

| Изменение | Почему |
|:--|:--|
| Регистрация `settings.section` (**Настройки → Gitea**) | место `settings.plugin.item` из upstream удалено в DSH 0.2.x и нигде не рендерилось |
| Форма настроек на маршрутах (`GET`/`POST /dsh-gitea/config`) с `writable` и Retry | зеркало браузерного `configForms` на не-loopback страницах только в памяти и скрывало все поля |
| `lib/http-guard.js`: смонтированный страж DSH Connection авторитетен для чтения и записи | допущенные запросы Tailscale/LAN проваливались в loopback-фолбэк и становились `403` |
| `scripts/dev-link-dsh.mjs` (`npm run dev:link`) | установки pnpm `link:` не разрешают DSH peer'ы плагина |
| переключатель Config `updates` + updater, нацеленный на npm-реестр Forgejo | updater ставит **наш** опубликованный пакет, а не upstream; переключатель защищает dev-checkout `link:` |
| регрессионный набор `test/` + `scripts/leak-scan.mjs` | публичное дерево upstream поставляет скрипт `npm test`, но не файлы тестов |
| `.forgejo/workflows/ci.yml` + `publish.yml` | проверки на каждый push в `master`; публикации по тегам идут в наш собственный npm-реестр |
| имя пакета без scope `dsh-gitea`, теги версий, этот README + `AGENTS.md` | форк — поддерживаемый проект, а не анонимный снимок |

Исправления инструментов, которые несёт форк: форматтеры вывода (обрезка
строк, голый `OK`, id меток), CRUD wiki и декодирование repo-contents,
семантика PR/слияния, QA-проход #19–#38 по поверхности инструментов и
исправление символической ссылки updater'а #44 в `0.8.1`.

## Разработка

```bash
npm run dev:link    # node scripts/dev-link-dsh.mjs
```

`plugin_manager` устанавливает локальный checkout как зависимость pnpm
`link:`, а pnpm не разрешает peer'ы связанного пакета из целевого каталога.
Скрипт находит работающую установку DSH (аргумент, `$DSH_PACKAGE_DIR` или
исполняемый файл `dsh`) и символически связывает пакеты, которые импортирует
этот плагин, в игнорируемый git `node_modules/`; он никогда не пишет в
установку DSH. Установке из реестра или git ничего из этого не нужно.

После изменения перезагрузите ту половину, которую трогали:

- **Host-половина** (`lib/index.js`, маршруты, обработчики): выключите и
  включите bundle (`plugin_manager action=set_bundle`) или включите HMR для
  checkout'а в патче **профиля** (`<profile>/cordis.patch.yml`, вне этого
  репозитория):

  ```yaml
  - id: hmr
    config:
      root: ["/path/to/dsh-gitea"]
  ```

  С таким root правки Host перезагружаются без перезапуска `dsh web`.
- **Клиентская половина** (`lib/client.js`): bundle отдаётся по запросу,
  поэтому жёсткое обновление (`Ctrl+F5`) подхватит его.

Проверки — `npm run check` это CI-гейт и то, что нужно запускать перед каждым
push:

```bash
npm run check        # npm test && test:leaks && node --check lib/client.js + lib/index.js
npm test             # node --test test/*.test.mjs
npm run test:leaks   # гигиена публикуемого дерева: приватные пути/scope/литералы токенов/кириллица
```

Два предупреждения:

- `lib/client.js` — сгенерированный вывод, единый браузерный bundle
  `window.__ModuleLoader__.load({ id, factory })`, а не исходник. Правки там —
  намеренные патчи исходника; upstream перегенерирует этот файл из приватного
  TypeScript, поэтому при синхронизации ожидайте конфликтов слияния (это наш
  самый большой diff) и заново применяйте наш блок.
- Здесь нет автоматизации браузера. Зелёный `npm run check` доказывает
  синтаксис и регистрацию, а не то, что видит человек; изменения UI всё ещё
  требуют ручной проверки в Web UI (пункт настроек, поля, сохранение,
  Git-бейдж).

## CI, релизы и версионирование

Четыре workflow Forgejo Actions в `.forgejo/workflows/`:

| Workflow | Триггер | Что делает |
|:--|:--|:--|
| `ci.yml` | push в `master`, ручной запуск | Node 22.6 → `npm run check`, затем `npm pack --dry-run` |
| `publish.yml` | тег `v*` (ручной = пробный прогон) | перезапускает проверки, требует, чтобы тег равнялся `v<package.json version>`, публикует в реестр Forgejo, пропускает уже опубликованную версию |
| `publish-npmjs.yml` | тег `v*` (ручной = только проверки) | те же проверки и проверка тега, затем `npm stage publish` в публичный npm-реестр; пропускается, пока нет секрета `NPMJS_TOKEN` |
| `release.yml` | тег `v*` (ручной = предпросмотр notes) | создаёт страницу релиза Forgejo для тега: имя и notes из `CHANGELOG.md`, плюс npm-tarball как скачиваемый ассет; никогда не перезаписывает существующий релиз |

- Страницы релизов генерируются, а не пишутся руками: `scripts/release-notes.mjs`
  превращает раздел changelog `## [<version>]` в заголовок
  (`v0.8.4 — Publish to npmjs through staged publishing`) и тело, и добавляет
  команду установки именно этой версии. Workflow использует автоматический
  Actions-токен (секрет `RELEASE_TOKEN` его переопределяет) и оставляет
  существующий релиз нетронутым, поэтому notes, отредактированные в UI,
  переживают последующие перезапуски. Та же страница несёт tarball:
  `.../releases/download/v<version>/dsh-gitea-<version>.tgz`.

- Реестры: Forgejo —
  `https://git.pvlb.dev/api/packages/dsh-plugins/npm/` (секрет `NPM_TOKEN`,
  токен Forgejo с областью `write:package`); npmjs — реестр по умолчанию
  (секрет `NPMJS_TOKEN`, гранулярный токен с *read and write (stage only)*).
  Пустой `NPM_TOKEN` валит задачу Forgejo; пустой `NPMJS_TOKEN` только
  пропускает публичную публикацию.
- `package.json` публичен (`publishConfig.access: public`), поэтому обе задачи
  публикуют один и тот же tarball; `files` ограничивает пакет `lib/`,
  `assets/`, `cordis.patch.yml`, `README.md`, `README.zh.md`, `README.ru.md`
  и `LICENSE`.
- Триггера `pull_request` намеренно нет: общий runner даёт job-контейнерам
  rootless Docker socket хоста, поэтому только события, контролируемые
  мейнтейнером, могут выполнять workflow.
- Только push тега публикует, и один тег публикуется в оба реестра — Forgejo
  напрямую, npmjs как staged-версию, которую мейнтейнер одобряет через 2FA
  (`npm stage approve <stage-id>`, или страница пакета на npmjs.com).
  `npm publish` был бы отклонён stage-only токеном.

Ритуал релиза:

```bash
# обновите package.json + CHANGELOG.md, закоммитьте
git push origin master
git tag -a v0.8.4 -m "dsh-gitea 0.8.4"
git push origin v0.8.4        # запускает publish.yml, publish-npmjs.yml и release.yml

# npmjs выполняет staged-публикацию: одобрите staged-версию через 2FA
# (или нажмите Approve на странице пакета на npmjs.com)
npm stage approve <stage-id>
```

Версионирование:

- Текущая версия форка — `0.8.8`, тег `v0.8.8`; более ранние сборки
  использовали `<upstream base>-dsh.<n>` (например, `0.7.40-dsh.7`),
  hotfix'ы могут использовать `0.8.8-dsh.<n>`. Помечайте тегом каждое
  состояние, живущее на сервере.
- Откат: `git checkout v0.8.8`, выключите и включите bundle, жёстко обновите
  страницу.
- `CHANGELOG.md` получает запись форка на каждый релиз; записи upstream
  остаются нетронутыми.
- Держите диапазон DSH в `peerDependencies` в соответствии с линией
  предрелизов Harness (сейчас он называет `>=0.1.7-rc.2 <0.2.0-0`,
  `>=0.2.0-rc.1 <0.3.0-0` и `>=0.2.1-0 <0.3.0-0`) — линия, не названная в
  диапазоне, оставит плагин молча не загруженным после обновления Harness.

Updater:

- Встроенный в UI updater читает `dist-tags.latest` из реестра Forgejo (у
  Forgejo 17 нет npmjs-подобного `/latest`), устанавливает tarball точной
  версии через одноразовый `.npmrc`, не трогающий реестр по умолчанию, и
  имеет двойной гейт: loopback-only запрос с заголовком
  `x-dsh-plugin-update` плюс переключатель Config `updates`. Этот профиль
  держит `updates: false` для `link:` checkout'а; включение позволяет
  следующему обновлению заменить этот checkout опубликованным пакетом.
- **Никогда не делайте реестр Forgejo реестром npm по умолчанию.** Иначе
  pnpm будет искать другие пакеты профиля (`dsh-cost-meter` и т. п.) там и
  получать 404. Оставьте npmjs по умолчанию и устанавливайте этот пакет по
  явному tarball-URL.
